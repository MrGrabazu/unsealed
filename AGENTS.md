# AGENTS.md — Unsealed

> **Unsealed — Crack & Collect**
> Jeu desktop gratuit qui reproduit les sensations d'ouverture de boosters Magic: The Gathering, avec des taux de tirage fidèles à chaque set et une économie virtuelle basée sur les prix réels du marché.

## 1. Vision du projet

- Reproduire le plaisir de l'ouverture de boosters **sans aucun coût réel** pour le joueur.
- Satisfaire la « collectionnite » : collection, complétion de sets, trophées exclusifs.
- Tout repose sur des **données réelles** : contenu des sets, taux de tirage, prix du marché.

### Identité

| Élément | Valeur |
|---|---|
| Nom du jeu | **Unsealed** |
| Accroche | **Crack & Collect** |
| Boutique in-game | **Boosterium** : lieu où l'on achète des boosters et revend ses cartes |

## 2. Contraintes non négociables

- **Aucune conversion** de la monnaie virtuelle ou des cartes vers quoi que ce soit de réel (pas d'échange monétaire, pas de cash-out). C'est ce qui garde le jeu hors du champ des réglementations sur les loot boxes.
- Respect de la **Fan Content Policy de Wizards of the Coast** :
  - afficher le disclaimer officiel de non-affiliation (écran « À propos » et page de lancement) ;
  - ne pas utiliser les logos Wizards / Magic ni de termes déposés (« Magic », « MTG », « Planeswalker »…) dans le nom ou l'identité de l'app ;
  - ne jamais laisser penser que l'app est officielle.
- Respect des **conditions d'utilisation de Scryfall** :
  - ne pas recadrer les images de cartes en masquant l'artiste ou le copyright ;
  - ne pas placer leurs données derrière un paywall ;
  - respecter leurs limites de requêtes et envoyer les en-têtes `User-Agent` et `Accept` requis.

## 3. Stack technique

| Couche | Techno | Rôle |
|---|---|---|
| Shell desktop | **Tauri** | Packaging, plugin updater pour les mises à jour |
| Backend | **Rust** | Tirage aléatoire, parsing des données, persistance, moteur d'achievements |
| Frontend | **React** | UI, animations d'ouverture, collection, Boosterium |
| Persistance | **SQLite** (`rusqlite` ou `sqlx`) | Collection, portefeuille, historique, progression des achievements |
| RNG | `rand` + `WeightedIndex` | Tirage pondéré, **RNG à seed** pour rejouer et tester |
| Animations | framer-motion (ou équivalent) | Révélation carte par carte, effets foil en CSS |

Règle générale : **la logique métier vit en Rust** (tirage, économie, achievements). React affiche et anime, il ne calcule pas les tirages.

## 4. Sources de données

### MTGJSON : configuration des boosters
- Les fichiers de set contiennent une clé `booster` qui décrit chaque type de booster (draft, set, play, collector…) :
  - les **sheets** (common, uncommon, rare/mythic, foil, land…), avec le poids de chaque carte ;
  - les **variantes de contenu** d'un booster et leurs poids respectifs.
- C'est la source principale des taux de tirage. **Vérifier le schéma exact dans la documentation MTGJSON actuelle** avant d'écrire le parser.
- Des fichiers de configuration locaux peuvent **surcharger ou corriger** la config MTGJSON pour un set donné.

### Scryfall : cartes, images, prix
- Métadonnées des cartes, images (CDN Scryfall, mises en cache localement côté client).
- Prix quotidiens (USD/EUR, foil / non-foil).

### Prix des boosters scellés
- Pas de source gratuite fiable : **décision actuelle = fichier de configuration édité à la main** par le mainteneur (un prix par set et par type de booster). Calcul à partir de l'**espérance de valeur (EV)** plus une marge = piste future, non retenue pour le moment.

## 5. Architecture de distribution des données

Le jeu est un client lourd : **il n'y a pas de serveur à héberger**. Les données sont construites deux fois par jour par une GitHub Action et publiées toutes prêtes (le **paquet de données**) ; l'app les télécharge, et ne les construit elle-même sur la machine du joueur, en tâche de fond, qu'à défaut.

```
[GitHub Action « Game data » (.github/workflows/data.yml), 3 h 17 et 15 h 17 UTC, ou à la main]
   └── data-builder --sets all --pack release-data : les données (comme ci-dessous), puis le paquet
         (core/src/pack.rs : un flux gzip, pour chaque fichier JSON de la racine et de sets/ son chemin puis ses octets, précédés de leur longueur ; le manifest en dernier)
   └── publiés sur la release « data » (une pre-release : l'updater de l'app, qui lit la dernière release, ne la prend jamais pour une version du jeu) : unsealed-data.pack.gz, puis manifest.json à côté
[Lancement de l'app]
   └── thread de fond (updater.rs)
         ├── lit le manifest local ; refresh_reason() décide : aucune donnée, set manquant, config changée (sets, types, boosters), ou données plus vieilles que maxAgeHours (24 h)
         ├── si oui, d'abord le paquet (pack::fetch_pack, `packUrl` de data.json) : lit le manifest publié (quelques Ko) ; pack_is_of_use() le prend s'il convient à ce jeu (même format de données, sets et types voulus) et s'il est plus récent que les données installées (ou de format différent) ; téléchargé dans le cache, vérifié (checksum gzip, chemins qui restent dans le dossier, manifest présent), installé fichier par fichier (`.incoming` puis renommé, le manifest en dernier, les sets absents du paquet supprimés)
         ├── à défaut (paquet absent, inutile, hors ligne, endommagé ; ou installé mais lui-même trop vieux, la construction du jour ayant échoué) : core::builder::build()
         │     ├── télécharge AllPrintings.json.gz de MTGJSON (~180 Mo, cache 7 jours) et le bulk Scryfall default_cards (cache par nom de fichier)
         │     ├── sélectionne les sets (liste explicite, ou "all" : types de setTypes, hors sets en ligne, avec un booster voulu)
         │     ├── valide chaque config de booster par simulation (sauf si déjà validée à l'identique : cache validated.json)
         │     ├── met de côté les sets invalides (`skipped` du manifest) au lieu d'échouer
         │     └── écrit sets/, prices.json, artists.json, guests.json, manifest.json (rename atomique, manifest en dernier)
         └── émet l'événement `data-status` (message + pourcentage estimé) ; l'UI affiche une barre de progression et se recharge à la fin
[Client Unsealed]
   └── premier lancement (aucun set, `get_data_info`) : écran « Préparation du jeu » (`Preparing.tsx`) à la place de l'accueil, jusqu'à la fin du build (avec l'avis de nouvelle version, qui peut être ce qui le débloque) ; en cas d'échec (hors ligne…), son message et « Réessayer » (`retry_data_update`, qui relance le build après un échec)
   └── ensuite, reste jouable sur les anciennes données pendant la mise à jour : bande dorée avec sa jauge en haut de la scène (`DataStatusBar`), ou une erreur non bloquante hors ligne
   └── filet de sécurité : sans aucun set pendant une préparation, Boosterium, Ouvrir et Collection montrent la préparation (`DataPreparing`) plutôt qu'une liste vide
   └── charge les images depuis le CDN Scryfall
```

- **Noms de fichiers réservés par Windows** : `CON`, `PRN`, `AUX`, `NUL`, `COM1`… désignent des périphériques, quelle que soit l'extension, avant Windows 11. Écrire `sets/CON.json` (Conflux) écrivait dans la « console », et le build échouait sous Windows 10 avec « Descripteur non valide (os error 6) » ; Windows 11 l'accepte, d'où un bug invisible en développement. Le fichier d'un set passe donc toujours par `set_file_name` (`CON_.json`) et se relit par `set_code_of_file` (catalog) ; un paquet de données qui contient un tel nom est refusé. Tout nouveau fichier nommé d'après une donnée (code de set, de série…) doit y passer.
- Les sets proposés et la fraîcheur maximale vivent dans `config/data.json` (surchargeable par un `data.json` du dossier de données).
- Les gros fichiers bruts sont gardés dans le dossier de cache de l'app ; les anciens bulks Scryfall (et les anciens fichiers MTGJSON par set) sont supprimés après chaque build.
- En debug, le core et ses dépendances lourdes sont compilés optimisés (`Cargo.toml` racine) : sinon le build lancé par l'app serait des dizaines de fois plus lent. Le core y est compilé sans incrémental : optimisé et incrémental, rustc laissait des symboles `anon.*.llvm.*` non résolus (erreurs de link jusqu'à un `cargo clean -p unsealed-core`).
- `UNSEALED_NO_UPDATE=1` désactive le job (développement).
- Le CLI `data-builder` appelle le même code (`core/src/builder.rs`) ; `--pack <dossier>` y écrit en plus le paquet et son manifest.
- **Paquet de données** : quelques Mo au lieu de centaines (AllPrintings et le bulk Scryfall), quelques secondes au lieu de minutes : indispensable pour une future version mobile. Le workflow `data.yml` garde le cache de validation (`validated.json`) d'un run à l'autre, crée la release « data » si elle manque, et publie avec le secret `RELEASE_TOKEN` (comme `release.yml`). Deux fois par jour pour que le paquet ait toujours bien moins que les 24 h au-delà desquelles un jeu juge ses données trop vieilles. Sans `packUrl` (ou vide), l'app construit toujours elle-même. Les données de Scryfall y sont redistribuées comme celles de MTGJSON, sans modification et gratuitement (décision du mainteneur).

## 6. Moteur de tirage

- Implémentation du tirage pondéré en Rust à partir des sheets et variantes de booster.
- **RNG injectable avec seed** pour des tests reproductibles.
- **Mode simulation** : ouvrir N boosters (ex. 100 000) côté Rust et comparer les taux obtenus aux taux attendus.
  - Sert de test de validation de chaque config de set.
  - Permet d'afficher l'**EV réelle** de chaque booster dans le Boosterium.
- **Ouverture en lot** (×10, ×100) avec animation accélérée qui ne ralentit que sur les grosses cartes. Indispensable pour rendre atteignables les gros paliers d'achievements. *Implémenté* : `Game::open_boosters` (une transaction par booster, s'arrête proprement si le stock s'épuise) et `BatchOpening.tsx` (carte « grosse » = mythique, rare foil ou prix ≥ 5 ; résumé final avec valeur totale, nouveautés, meilleurs tirages).

## 7. Économie (Boosterium)

- **Monnaie du jeu : les Sceaux** (*Seals*, « Siegel », « Sellos », « Sigilli »), fictive, pour marquer que rien n'a de valeur réelle. En interne, tout reste en centimes de la **devise du marché** (`currency.market` de `economy.json` : USD ou EUR, source des prix Scryfall) ; l'interface affiche `centimes × sealsPerCent` (1 par défaut : 7,61 $ → 761 Sceaux), en nombre entier, toujours avec la même **pièce dorée en forme de sceau** (`app/src/money.tsx`) : une couleur variant avec le montant faisait croire à plusieurs monnaies. Là où un élément est impossible (listes déroulantes, infobulles, notifications), le montant s'écrit en toutes lettres.
- Les textes de configuration écrivent les montants en jetons `{cents:N}` (ex. descriptions d'achievements), convertis à l'affichage : ils restent justes si le ratio change. Un test interdit le « $ » dans les achievements et exige les mêmes jetons dans chaque traduction.

- **Achat** des boosters au prix marché (ou prix configuré).
- **Revente** des cartes à un **pourcentage du prix marché** (type buylist). **Valeur actuelle : prix du marché actuel − 20 % (soit 80 %)**, à équilibrer et à garder configurable.
  - Objectif : comme dans la réalité, la plupart des ouvertures sont perdantes, et un gros tirage procure un vrai plaisir.
- **Présentation** (écran du « Comptoir », voir 8 ter bis) : à gauche, dans le cadre « Boutique », chaque set est un **emplacement illustré** (art crop de la carte phare, ou son symbole en grand ; médaillon du symbole, étoile, nom, prix « dès », ruban « Nouveau » les 45 jours qui suivent sa sortie), avec recherche et filtres par année et budget ; à droite, le **set choisi** (cartouche à son nom, illustration créditée, symbole, date, puis ses produits : types de booster triés Play → Draft → Set → Collector, chacun avec son prix, sa reprise et sa tendance), et **une seule action** : « Acheter · total », avec la quantité (sélecteur, 1 à 100) et « Ouvrir aussitôt » (achète puis ouvre le premier). Clavier : ⏎ achète, + et − changent la quantité, F met le set en favori. L'**étoile** d'un emplacement (creuse, dorée pour un favori) met le set **en favori** : les favoris forment une section « Favoris » au-dessus de « Tous les sets » (chacune du plus récent au plus ancien, un set n'apparaissant que dans l'une) ; la liste est gardée dans la partie (`save_meta` `pinned_sets`, commandes `get_pinned_sets` / `set_pinned_sets`). La vente de **boîtes de boosters** est prévue plus tard : elles s'ajouteront aux produits d'un set.
- **Illustration des sets** : l'*art crop* Scryfall de la carte phare (la plus chère des boosters principaux, choisie au build : `featured` du manifest ; parmi les cartes du set, ou à défaut parmi celles qu'il réimprime d'autres sets : les Mystery Boosters ne contiennent que des cartes de « PLST » et autres). Toutes les lignes de set ont la même allure, illustrées ou non (92 px de haut, prix « à partir de » dans une pastille), et leurs coins dorés sont dessinés par-dessus l'illustration (`.shop-set::after`), repliées comme dépliées. Règles Scryfall : afficher l'artiste et le copyright à côté, ne jamais flouter, désaturer ni recolorer l'image. Dans le Boosterium, elle sert de fond à la moitié droite de chaque ligne de set, en pleine opacité ; un dégradé de la couleur du panneau recouvre son bord gauche pour garder le texte lisible (on ne baisse jamais l'opacité de l'image elle-même).
- **Symboles d'extension** : autorisés par décision du mainteneur (la Fan Content Policy ne les vise pas explicitement). Source : `icon_svg_uri` de l'API Scryfall des sets, enregistré au build dans le manifest. Affichés tels quels, sans modification ; le SVG étant noir, il est posé sur une pastille claire.
- **Une matière par type de booster** (`wrapperFinish` de `boosterKinds.ts`, maquette validée `.cache/da/v6.html`), pour distinguer d'un coup d'œil les types d'un set et suivre leur prix ; même taille, mêmes bords dentelés et même illustration (celle du set) pour tous : **Draft** en papier mat (couleurs éteintes, sans reflet, garnitures bronze) ; **Play** et booster unique des vieux sets en foil (l'emballage d'origine) ; **Set** en foil plus brillant, liseré et ruban argentés ; **Collector** en laque noire, bords dentelés dorés, filet holographique sous les bords, fenêtre et sceau dorés, ruban arc-en-ciel, léger halo. Appliqué partout où un booster est dessiné : la réserve et le booster prêt (`Wrapper`, classes `finish-*` de `comptoir.css`), l'ouverture classique (`Pack.tsx`) et l'emballage 3D (`packTexture` / `stripTexture` de `scene/textures.ts`, `drawSeal(…, golden)` de `canvasArt.ts`).
- **Onglet d'ouverture** (`SealedBoosters.tsx`) : la **réserve**, où les boosters scellés se tiennent debout (emballage original `Wrapper` : foil à la teinte du set `hueOf` dans la matière de son type, art dans une fenêtre dorée, ruban du type, sceau ; leur nombre en pastille), plus une place « Plus de boosters ? » qui mène au Boosterium ; à droite, celui qu'on a choisi **flotte dans la lumière**, avec son coût, sa valeur de reprise (gain ou perte), sa tendance, puis « En ouvrir un » en cire, l'ouverture rapide, les lots (×10, ×100) et la revente. Clavier : ⏎ ouvre, Q ouvre en rapide. Vide : un cadre avec un lien vers le Boosterium. Une ouverture s'affiche une seule fois (dans un cadre au nom du set et du type), quitter l'onglet la referme.
- **Ouvrir un booster, comme en vrai** (`PackOpening.tsx`) : le booster scellé s'affiche d'abord (`Pack.tsx`, emballage **original** : sachet métallisé à la teinte du set, bords dentelés, fenêtre sur l'art de la carte phare ; les vrais emballages portent le logo Magic et ne sont pas dans les sources). Il n'est **consommé qu'à la déchirure** (le tirage a lieu à ce moment-là). Les cartes forment une pile face cachée : un clic (ou Espace) retourne la carte du dessus, un autre la pose dans la rangée du dessous ; les cartes viennent dans l'ordre d'un vrai booster de leur type (MTGJSON n'en donne aucun : `reveal_rank`, d'après la rareté et le nom de la feuille tirée), le token toujours en dernier. **Draft** et vieux boosters : communes, peu communes, rare/mythique, foil, terrain de base. **Play** (emplacements n°1 à 15 du wiki MTG) : communes, Special Guest / The List, peu communes, wildcard, rare/mythique, terrain, wildcard foil. **Set** (« chapitres » du wiki) : terrain d'abord, communes/peu communes, showcase commune/peu commune, wildcards, rare/mythique, foil, puis The List avant le token. Pages du wiki recopiées (format wiki) dans `.cache/wiki/` (draft, play, set, collector, theme), non commitées. **Collector** (presque tout est foil) : par rareté seulement — aucune source trouvée sur leur ordre physique, à corriger si on en trouve une. Les rares, mythiques et foils ont un effet lumineux. À la fin, un clic sur une carte ouvre sa fiche. L'ouverture par lot (×10, ×100) reste accélérée.
- **Vendre après l'ouverture** (`BoosterSale.tsx`, dans les trois ouvertures une fois toutes les cartes vues) : un bouton « Vendre » sous chaque carte (au prix de rachat calculé à l'ouverture, `sellValueCents` d'`OpenedCard`), la carte vendue passe en grisé avec « Vendue » ; et « Vendre tout le booster » dans la barre, avec le montant des cartes restantes et un second clic pour confirmer, puis « Vendu pour… ». Un simple `sell_cards` (les exemplaires d'une même carte et finition en une requête) ; le portefeuille et les succès sont rafraîchis.
- **Écran d'ouverture** (maquette A de `.cache/da/v4.html`, « la table de déballage ») : à gauche, le booster seul sous la lumière dans un cadre à son nom (scène 3D ou ouverture classique), avec ses pastilles (prix du jour, reprise, nombre restant en réserve) ; à droite, le panneau « 🎲 Parier sur ce booster », **toujours déplié** (`BetSlip` en mode `panel`) : une petite carte par pari (interrupteur de pause, description, cote, mise modifiable, gain, chance, 📌 pour le garder, ×), « + Nouveau pari » qui ouvre le constructeur à sa place, et le total misé ; en bas, « Déchirer le booster » en cire (`tearRequest` : la scène 3D le déchire seule depuis la gauche, comme d'un clic), l'ouverture rapide (avec les paris du panneau) et le retour à la réserve. Clavier : Espace déchire, Q ouvre en rapide, Échap revient à la réserve. Une fois déchiré, le panneau ne montre plus que les paris placés (`locked`) et la mise en page ne bouge pas jusqu'au bilan (la scène 3D garde sa taille) : les cartes déjà vues s'alignent dans une **colonne étroite posée sur le bord droit de la scène** (`.seen-strip`, en position absolue : elle ne prend aucune place, le booster et la pile restent centrés ; la dernière en haut, cliquable pour sa fiche), et non plus dessous, où chaque nouvelle rangée faisait rétrécir la scène.
- **Barres de défilement** (`comptoir.css`) : fines (8 px), une baguette dorée presque invisible au repos, qui s'affirme au survol de la zone qu'elle fait défiler, piste transparente.
- **Paris sur les boosters** (en Sceaux virtuels uniquement) : sur le booster scellé, avant de le déchirer, le panneau des paris (`BetSlip.tsx` ; ailleurs il reste un bulletin replié par défaut, qui affiche le nombre de paris et la mise), **sans liste préremplie** : un constructeur où chaque pari est fait de **conditions qui doivent toutes être vraies** (combiné). Une condition porte soit sur **les cartes** (*au moins / exactement / au plus / aucune* N cartes qui vérifient un filtre : catégorie cartes / jetons / cartes d'art / tout, raretés, types — terrain, terrain de base, créature, éphémère, rituel, artefact, enchantement, planeswalker, bataille —, couleurs — dont incolore et multicolore ; celle d'un terrain est son identité de couleur : une Forêt est verte —, finition, traitement full art ou cadre spécial, prix min/max dans sa finition, carte précise par son numéro), soit sur **la valeur du booster** (au moins / au plus X, raccourcis « rentable » / « perdant » au prix du booster du moment). Autant de paris qu'on veut par ouverture ; la cote se calcule en direct pendant qu'on compose. Les cotes sont les **vraies chances** : 1 / probabilité, moins la marge de la maison (`betting.houseMarginPercent` d'`economy.json`, **0 = cotes justes**, choix du mainteneur). La chance est **exacte** pour un pari d'une seule condition « au moins 1 » ou « aucune » (`betting::any_probability` : sur une feuille sans doublon, un groupe de cartes n'est pas tiré exactement comme une seule carte de poids égal à la somme du groupe — course d'horloges exponentielles —, puis `sim::inclusion_probabilities`) ; sinon elle est comptée sur 100 000 boosters simulés à seed fixe (`simulatedBoosters`, `SimulatedPacks`), gardés en cache par type de booster jusqu'au prochain changement de données ou de prix, et le pari n'est coté que s'il a réussi et échoué au moins `minSimulatedHits` fois. Un pari sans cote dit pourquoi (`unpriced` de `BetChance`) : **toujours gagné** (« au moins une foil » sur un Play, Set ou Collector Booster, qui en ont toujours une), **impossible** (une foil avant les foils), ou trop rare ou trop sûr pour la simulation ; une chance exacte à moins de 1e-9 de 0 ou de 1 est certaine (`CERTAIN` : les sommes sur les feuilles donnaient 99,9999999 %, coté ×1,00). Test sur les vraies données : `cargo test --release -p unsealed-app foil_bet -- --ignored --nocapture`. Mise minimale `minStakeCents`. Un 📌 garde un pari **d'une ouverture sur l'autre** (gardé dans la partie, `save_meta` `kept_bets` ; un pari qui nomme une carte ne vaut que pour son set) ; il s'applique aussi à l'ouverture rapide et par lot ; les autres paris ne valent que pour le booster en cours. Une case sur chaque ligne du bulletin **met un pari en pause** sans le perdre ni changer sa mise (`active` de la ligne et du pari gardé) : il n'est pas placé tant qu'il est en pause, ouverture rapide et par lot comprises. Un pari qui ne peut pas être placé **sur le booster ouvert** est **laissé de côté** sans mise prélevée, et le booster s'ouvre quand même (`OpenedBooster::skipped`, avec sa raison, listé dans le bilan) : impossible à coter sur ce booster (un 📌 « au moins 1 foil » sur un Play Booster, qui en a toujours une), mise sous le minimum, ou **plus assez de Sceaux** (les paris sont payés dans l'ordre du bulletin tant que le solde le permet). Avant, chacun de ces cas faisait échouer l'ouverture. Si une ouverture 3D échoue malgré tout, la scène repart avec le booster scellé (`attempt` de `PackOpening3D.tsx`). Données : `types` (types et surtypes en minuscules) et `colorIdentity` des cartes (format de données 8). La mise est prélevée à la déchirure, dans la même transaction que l'ouverture (`Store::open_sealed_with_bets`, refusée si on ne peut pas la payer) ; le pari est réglé par le tirage, mais le **gain n'est versé qu'une fois toutes les cartes vues** (`Store::pay_bets` à la fin de `reveal_cards`, après chaque booster d'un lot, et au chargement d'une partie fermée en cours d'ouverture) : le portefeuille ne dévoile rien. Le bilan (`BetResults.tsx`, regroupé par pari pour un lot) s'affiche alors. Table `bets` (migration 10), mouvements `bet_stake` / `bet_win` dans l'historique, bilan dans les Stats, événement `BetSettled` (`won`, `conditions`, `stakeCents`, `payoutCents`, `probabilityPermille`) pour de futurs succès. Core : `core/src/betting.rs` ; jeu : `game/betting.rs` (commandes `get_bet_context`, `get_bet_chance`, `get_kept_bets`, `set_kept_bets`) ; texte d'un pari : `describeBet` de `bets.ts`. Les drapeaux `fullArt` / `specialFrame` des cartes viennent de `isFullArt`, `borderColor` et `frameEffects` de MTGJSON.
- **Résultat d'une ouverture** (`OpeningResult.tsx`, Comptoir) : une fois la dernière carte partie (3D : `onFinished` de `PackOpening3D`, après son envol ; classique : 0,9 s après la dernière carte posée ; rapide : aussitôt tiré), l'écran montre à gauche la main étalée (`RevealedCards`, deux rangées, vente carte par carte) et à droite le **bilan** : valeur du booster en grand, gain ou perte sur son prix du jour, nouvelles cartes, meilleure carte, ce que le Boosterium en donne, les paris réglés (`BetResults`), puis « Vendre tout le booster », « Ouvrir le suivant », l'ouverture rapide et le retour à la réserve. Le lot (×10, ×100) garde son résumé (`BatchOpening`).
- **Ouverture rapide** (« ⚡ Ouverture rapide », sur chaque booster scellé et dans le bilan) : pas de déchirure ni de pile, le booster est tiré aussitôt et ses cartes distribuées d'un coup sur l'écran de résultat, dans l'ordre d'un vrai booster, le son final étant celui de la meilleure carte (`bestCard`) ; tout est vu d'un coup (achievements compris). Le backend distingue les ouvertures regardées des autres : `open_booster` (commande Tauri) prend `animated`, l'événement `BoosterOpened` porte `animated` (faux pour l'ouverture rapide et par lot), d'où les métriques `boosters_watched` / `boosters_rushed` et 4 achievements secrets (500 et 1 000 de chaque).
- **Ouverture en 3D** (par défaut, désactivable dans Options : `app/src/settings.ts`, repli sur l'ouverture classique sans WebGL2) : scène three.js / react-three-fiber chargée à la demande (`PackOpening3D.tsx`, `app/src/scene/`). Le booster s'incline vers la souris et se secoue quand on le tient. On déchire la bande du haut en glissant le long d'elle (ou d'un simple clic sur le booster : elle se déchire seule depuis le côté cliqué) : elle se décolle d'un seul tenant depuis le côté de départ, puis tombe. Une fois déchiré, la pile (cachée derrière la face de l'emballage) sort par le haut **côté dos**, comme d'un vrai booster, puis l'emballage vide tombe pendant que la pile se pose au centre ; elle est alors retournée d'un bloc autour de son milieu (`PILE_TURNS`, 0,5 s, son de carte retournée) pour montrer sa première carte. Sans art crop, la fenêtre du booster montre un fond rayonnant aux couleurs du set autour de son symbole d'extension (ou de son code). Les cartes sont **rigides et épaisses** (`cardMaterial.ts` : dalle extrudée à coins arrondis, tranche, foil irisé suivant la souris). Quand l'emballage tombe, la pile est rapprochée du joueur (×1,5, `CARD_ZOOM`, glissement corrigé de ce facteur) pour mieux lire les cartes ; le cadre (680 px) et le champ de la caméra (40°) leur laissent une marge en haut et en bas. Les cartes vues en grand (scène, fiche de détail) utilisent l'image « large » de Scryfall (672 px, `largeImage` de `images.ts`), les listes la « normal » (488 px). La pile s'incline d'un bloc (survoler ne dévoile rien) ; on fait glisser la carte du dessus dans n'importe quelle direction (au-delà de ~1,3 unité ou d'un geste vif, elle part ; sinon elle revient), un clic ou Espace l'envoie. Une carte compte comme vue (achievements) quand elle arrive sur le dessus ; ses effets (halo des grosses cartes, halo arc-en-ciel et étincelles des foils) n'apparaissent qu'à ce moment, jamais pour les cartes encore cachées. La scène tient elle-même l'index de la carte du dessus (`current`), sans attendre React, pour qu'une carte partie ne réapparaisse pas une image sur la pile. La dernière reste ~2 s puis s'envole ; la scène laisse alors place à la liste des cartes avec la valeur du booster.
- **Effet foil, le même partout**, voulu réaliste (la carte reste lisible) : un arc-en-ciel discret (bandes inclinées de 18° par rapport à la verticale, qui défilent lentement) pleinement visible dans une large bande de lumière qui balaie la carte, plus discret ailleurs, avec un reflet blanc diffus. En CSS, « overlay » à 85 % (60 % hors de la bande) : « soft-light » est invisible sur une vignette. Le shader 3D, vu en grand, reste en « soft-light » (40 % hors de la bande). En 3D, la bande suit la souris, comme quand on incline une vraie carte. En CSS (`.foil-sheen` de `styles.css` : ouvertures, listes, Collection dès qu'un exemplaire foil est possédé) et dans le shader des cartes 3D (`cardMaterial.ts`), qui reprend les mêmes valeurs : les modifier ensemble. Dans les listes, un halo léger qui parcourt l'arc-en-ciel entoure en plus chaque foil.
- **Foils spéciaux** (maquette validée `.cache/da/v9.html`, `make-v9.js`) : galaxy, surge, double rainbow, textured, fracture, halo, oil slick, gilded, silver, mana, neon ink, ripple… sont des **impressions à part** (leur propre numéro, foil seulement, déjà dans les feuilles des boosters avec leurs taux et leur prix Scryfall), reconnues à leur `promoTypes` MTGJSON ; l'**etched** est une **finition** (`etched`, 827 cartes), dont Scryfall donne le prix dans `usd_etched` (aucun prix etched en euros), lu comme prix foil. Au build, `foil_kind` (`FOIL_KINDS` de `catalog.rs`) l'enregistre dans le `CardEntry` (format de données 12) ; le jeu le transmet (`foilKind` d'`OpenedCard`, `CollectionCard`, de la fiche). Interface : `FoilSheen` de `foils.tsx` (remplace `sheenClass`) pose l'effet (`fx-*` de `foils.css`, parties dessinées en SVG à seed dans des propriétés CSS : champs d'étoiles, éclats, relief, huile), son halo, et le **nom du foil en badge** en bas à droite (en anglais, comme les cartes ; à la place de « Foil » dans la Collection ; sa taille suit la largeur de la carte, `cqw` d'une container query : environ 9 px dans la grille, 11 px au plus, et il disparaît sous 120 px de large, sur les emplacements des Ensembles ou les cartes vues à côté d'une ouverture) ; la fiche nomme le prix (« Galaxy foil » au lieu de « Foil »). Step-and-compleat, raised, first place, invisible ink… gardent le foil habituel avec leur nom. L'ouverture 3D a les mêmes effets dans le shader des cartes (`uKind` de `cardMaterial.ts`) ; pour le galaxy, exactement les mêmes étoiles qu'en 2D : les trois champs (`STAR_FIELDS` de `foils.tsx`, à seed) dessinés une fois dans une texture, un champ par canal de couleur, que le shader fait scintiller au rythme de `STAR_TWINKLES`, et la même nébuleuse ; `node .cache/shader-check.js` compile ce shader dans Edge headless (SwiftShader) pour vérifier qu'il n'a pas d'erreur. Recensement des foils d'après le bulk Scryfall : `node .cache/foil-kinds.js`.
- **Historique des prix des boosters** : à chaque nouveau `prices.json`, le prix de chaque booster est enregistré en SQLite (table `price_history`, un point par snapshot `updatedAt`). Le Boosterium et les boosters scellés affichent les 30 derniers points en sparkline, avec la variation depuis la mise à jour précédente (`PriceTrend.tsx`).
- **Capital de départ** et **petit revenu quotidien** pour éviter un game over définitif.
- **Revenu de la collection** (`game/income.rs`, `income` d'`economy.json`) : la collection rapporte **chaque minute `percentPerMinute` % (0,1) de sa valeur de rachat**, sur les seuls vrais prix du marché (prix estimés et prix de repli ne rapportent rien), sans contrepartie : plus elle vaut, plus elle rapporte, ce qui pousse à garder ses belles cartes. L'interface appelle `collect_income` à l'arrivée dans la partie, puis à peu près chaque fois qu'un Sceau entier est gagné (60 s / gain par minute, entre 1 s et 60 s) : à chaque versement, un « +N » doré s'élève du solde (`.income-float`), qui grandit aussitôt avec une petite pulsation (le portefeuille complet et les succès débloqués ne sont relus qu'une fois par minute) ; chaque appel paie le temps écoulé depuis le précédent, **plafonné à `offlineCapMinutes` (480 = 8 h)** : la collection rapporte aussi jeu fermé, sans qu'un retour après un mois fasse tout sauter. La fraction de centime est gardée d'un paiement à l'autre (`save_meta` `income_paid_until`, `income_carry`, `income_value`) ; le tout premier appel ne fait que démarrer le compte. Pendant la révélation d'un booster, le revenu garde la valeur d'avant (sinon le taux affiché trahirait une grosse carte). Les versements d'une même heure se cumulent sur une seule ligne `income` de l'historique (`Store::credit_income`). Le taux est affiché à droite du solde, sur la même ligne (« +16 / min », arrondi à l'entier supérieur : jamais de fraction de Sceau à l'écran ; infobulle avec la valeur et le plafond) ; après au moins 5 minutes d'absence, un petit cadre « Bon retour » descend sous le solde, dans la sangle (`AwayIncome` de `GameScreen.tsx` : « +N » en grand, la durée, bruit de pièces ; il ne décale rien et se ferme d'un clic ou après 20 s). Un bandeau en haut de la scène, essayé avant, poussait tout vers le bas et passait inaperçu. Événement `IncomeEarned` (`amountCents`), métrique `income_cents`, 3 succès (1 000, 10 000 et 100 000 Sceaux gagnés), tous obtenables quelle que soit la façon de jouer. Une avance quotidienne avec malus puis un prêt à échéance avec saisie ont été essayés avant et abandonnés : trop de contraintes, qui gâchaient le plaisir d'ouvrir. Il en reste la table `debt_movements` (migration 11, plus lue) et les mouvements `advance` / `debt_repaid` des parties qui les ont utilisés.
- Tous les paramètres économiques sont **configurables** (pas de valeurs en dur dans le code).

## 8. Achievements

### Moteur
- **Définis dans des fichiers de configuration** (condition, seuils, récompense) : ajouter un achievement ne doit nécessiter aucune modification de code.
- **Moteur événementiel en Rust** : le jeu émet des événements, et chaque achievement écoute ceux qui le concernent.
  - Exemples d'événements : `BoosterOpened`, `CardAcquired`, `CardSold`, `SetCompleted`.
- Progression et compteurs persistés dans SQLite.

### Catégories
- **Paliers de volume** : ouvrir 10 / 100 / 1 000 / 10 000 / 100 000… boosters ; cumuler X de valeur ouverte ; revendre X cartes.
- **Complétion** : set complet, toutes les rares d'un set, set entièrement foil, bloc ou année complète.
- **Tirages remarquables** : mythique foil, deux mythiques dans un même booster, carte au-dessus d'une valeur seuil.
- **Cachés / humoristiques** : booster le moins rentable de l'historique, longue série sans mythique, revente par erreur de sa carte la plus chère…

### Récompenses
- **Bonus d'argent virtuel** : à calibrer sur l'économie. Préférer des récompenses proportionnelles ou des **boosters offerts** à des montants fixes.
- **Cartes d'achievement exclusives** (voir section 2) :
  - obtenables **uniquement** via les achievements ;
  - rareté proportionnelle à la difficulté de l'achievement ;
  - forment leur propre collection « méta », dont la complétion est l'achievement ultime.

### 8 bis. État actuel de l'implémentation

- **Définitions** : `config/achievements.json` (112 achievements, dont 16 secrets ; 16 portent sur les cycles, voir section 9 ; dont 8 pour les jetons et les cartes d'art : `SetProgress` porte aussi `tokensCompletionPermille`, `artsCompletionPermille` et `signedArtsCompletionPermille` ; un test exige moins de mythiques que de communs). Aucun achievement quasi impossible (tirer l'Anneau unique…) : l'ultime « Unsealed » demande tous les autres. **Aucun achievement ne doit en exclure un autre** (« ne jamais emprunter », « ne jamais vendre »…) : tous doivent pouvoir être obtenus dans une même partie, quelle que soit la façon de jouer (le moteur n'a d'ailleurs que des conditions qui ne font que progresser).
- **Écran** (`Achievements.tsx`, Comptoir) : à gauche le « cabinet des succès » (cartouche avec le compte, filtres Tous / Débloqués / À débloquer / Secrets, jauge de progression, grille des cartes) ; à droite le succès choisi (par défaut le dernier débloqué) : sa carte en grand, son numéro et sa rareté, son objectif en clair, sa progression, sa récompense et sa date de déblocage ; un secret verrouillé n'y montre que sa rareté. Rien n'est écrit sous les cartes de la grille : la carte elle-même porte la progression (compteur en petit au-dessus de sa barre, la description passant alors sur 2 lignes). Un `achievements.json` dans le dossier de données le remplace.
- **Moteur** : `core/src/achievements.rs`. Des *métriques* (`sum`, `max`, `streak`, `distinct`) sont alimentées par les événements ; une *condition* débloque sur seuil de métrique, sur un événement filtré, ou `allOthers` (l'ultime). Un déblocage émet `AchievementUnlocked`, ce qui permet des méta-achievements.
- **Événements émis par le jeu** (`app/src-tauri/src/game/achievements.rs`) : `BoosterOpened`, `CardAcquired`, `SetProgress` (complétion globale, rares, mythiques, foil, collector extras, jetons, cartes d'art et leurs versions signées), `YearProgress` (sets complets parmi ceux proposés de la même année), `CardSold`, `SaleCompleted`, `BoosterBought`, `BoosterSold`, `CharityClaimed`, `BalanceChanged`, `BetSettled`, `IncomeEarned`. Ajouter un champ ou un événement demande du code ; ajouter un achievement n'en demande pas.
- **Pas de spoiler à l'ouverture** : le tirage a lieu à la déchirure, mais ses événements attendent (`Game::reveal_cards`). Chaque `CardAcquired` est émis quand sa carte est retournée ; les événements du booster entier (`BoosterOpened`, `SetProgress`, `YearProgress`, `BalanceChanged`) avec la dernière carte. Toute autre action, la fermeture de l'ouverture ou de la partie (`Drop`) émet ce qui reste. L'ouverture par lot émet tout d'un coup, et l'interface retient les notifications jusqu'au résumé.
- **Récompenses** : `cashCents` et/ou boosters offerts (`setCode` explicite ou `"latest"` = le set le plus récent qui propose ce type de booster, pas forcément le plus récent de tous : MBC n'a que du `draft`). Payées une seule fois, dans la même transaction que le déblocage.
- **Cartes** : dessinées en SVG par `app/src/AchievementCard.tsx`, dans le cuir du thème (maquette V3, `.cache/da/v3.html`) : carte aux coins arrondis, **liseré au métal de la rareté** (étain, argent, or, feu ; halo pour les rares et mythiques débloquées), cuir grainé, double filet doré et surpiqûre, filigranes du thème aux quatre coins, numéro sur une petite plaque et losanges de rareté, **médaillon** (couleurs, motif procédural selon l'id et emblème propres au succès) clouté et encadré de deux ailes dorées, nom en Cinzel (sur deux lignes s'il est long), losange, objectif ou jauge de progression, et la **rareté sur un ruban** qui passe sur le bord inférieur ; reflet holographique sur les mythiques débloquées, carte grisée tant qu'elle est verrouillée. Look volontairement différent de toute mise en page de carte à jouer. Les listes `EMBLEMS` et `PALETTES` de `core/src/achievements.rs` doivent rester synchronisées avec celles du composant.
- **Secrets** : tant qu'ils sont verrouillés, seuls la rareté et le numéro sont exposés (nom, objectif, récompense et visuel restent cachés, côté Rust).
- **Complétion foil** : ne compte que les cartes imprimées en foil (`finishes`). **Année complète** : tous les sets proposés de l'année, avec au moins 2 sets pour l'achievement livré.
- **Pas encore fait** : complétion par bloc (aucun set proposé n'appartient à un bloc, les blocs ont disparu en 2019), illustrations personnalisées par achievement.

## 7 ter. Curiosités (artefacts)

- **Des objets uniques** qui donnent un effet permanent sur l'économie, et se collectionnent comme des succès : **30**, dont certains très rares, pour qu'on ne puisse pas presque tout avoir dans les premières heures. Le jeu est **casual** : un artefact est un bonus, jamais un passage obligé (on doit pouvoir jouer sans), assez rare pour qu'en gagner un fasse plaisir, sans demander de grinder pour que le jeu devienne intéressant. **Ils ne changent jamais les taux de tirage** : un artefact trouvé dans un booster est tiré après ses cartes, avec le même RNG, sans toucher au contenu.
- **Définis en config** (`config/artifacts.json`, traductions `config/artifacts.<langue>.json` : nom, effet, texte d'ambiance ; surchargeables depuis le dossier de données) : `id`, `rarity` (common…mythic), `glyph` (dessin original d'`ArtifactGlyph.tsx`), `source`, `requires` (artefacts à posséder avant), `effects`. Les montants des textes en jetons `{cents:N}`. Core : `core/src/artifacts.rs` (validation, `Bonuses` qui cumule les effets, `roll_booster`) ; tests `core/tests/artifacts.rs` (config valide et traduite, succès existants, ordre des clés, couronne).
- **Sources** : `shop` (prix fixe, vendu au Boosterium), `booster` (`oneIn`, éventuellement limité à des types de booster et à des sets sortis avant une date, `releasedBefore` ; au plus un par booster, le plus rare d'abord), `achievement` (donné au déblocage de ce succès), `allOthers` (la **Couronne du Comptoir**, quand tous les autres sont là : le solde porte alors un cadre doré).
- **Effets** : taux de revente (`sellRate`, le meilleur l'emporte : par rareté, au-dessus d'un prix, foil seulement, ou cartes des sets sortis avant une date ; une date inconnue n'est jamais ancienne ; toujours ≤ 100 %, sinon ouvrir deviendrait une planche à billets, les boosters coûtant leur espérance de valeur), bonus sur la revente des doublons, remise sur les boosters (par type, ou sets sortis avant une date ; cumulées, plafonnées à 90 %), bonus de revenu (fixe, ou par set complet avec un plafond, qui s'additionnent), multiplicateur du revenu appliqué après tous les bonus (`incomeMultiplier` : l'Œuf de Dragon, ×2), plafond hors ligne, aide quotidienne multipliée, pénalité d'annulation réduite, bonus sur les paris gagnés, une mise perdue rendue par jour (`bet_refund`).
- **Chaîne des clés** (Collector Boosters uniquement) : bronze 1/30, argent 1/75, or 1/150, diamant 1/225, obsidienne 1/375 (environ 855 Collector pour les cinq), chacune demandant les précédentes, −10 % sur les Collector chacune (cumulées : moitié prix avec les cinq, ce qui rend les Collector rentables en fin de chaîne, récompense assumée). L'**Œuf de Dragon** (1/750 Collector) n'apparaît qu'au porteur de la clé d'obsidienne. Les taux des boosters ont été calibrés pour un joueur casual (ordre de grandeur : un Collector coûte 2 500 à 4 000 Sceaux, on démarre avec 10 000) : des taux de 1/2 000 et plus demandaient des dizaines de millions de Sceaux.
- **Jeu** : `game/artifacts.rs` (bonus gardés en cache et recalculés à chaque acquisition, vues `ArtifactView` : `owned` / `shop` / `hidden`, un artefact caché ne montrant que sa rareté et le type de sa source) ; table `artifacts` (migration 12), mouvements `artifact_purchase` et `bet_refund` dans l'historique, événement `ArtifactAcquired` pour de futurs succès. Commandes `get_artifacts`, `buy_artifact`, `take_given_artifacts`.
- **Interface** : onglet **Curiosités** (`Curiosities.tsx`, entre Succès et Stats) : le cabinet (vitrine de bois, étagères de velours, chaque artefact sous sa cloche de verre ; possédé il brille, en vente il est éteint, sinon c'est une silhouette « ? ? ? »), filtres Tous / Possédés / En vente / À découvrir, et à droite l'artefact choisi sous la lumière. Au Boosterium, un emplacement « Curiosités » au-dessus des sets ouvre la liste de ceux en vente. Obtenir un artefact (booster, succès, achat) a **son propre moment** (`ArtifactReveal.tsx` : il monte sous sa cloche, rayons, fanfare), après le bilan de l'ouverture.

## 7 bis. Historique et annulation

- **Onglet Historique** (`History.tsx`, Comptoir) : le **livre de comptes**, tous les mouvements du portefeuille (table `ledger`) regroupés par jour (« Aujourd'hui », « Hier », puis la date), chacun avec son icône, son heure et son montant (vert ou rouge), filtres Tout / Achats / Ventes / Revenus / Paris ; à droite le mouvement choisi : montant en grand, ses articles (achats et ventes, table `transactions`, migration 8 : articles en JSON, `TxItem`) et, tant que c'est possible, son annulation en cire avec sa pénalité (second clic pour confirmer). Les ventes antérieures à cette version n'ont pas de détail et ne s'annulent pas.
- **Annuler une vente** : on récupère cartes ou boosters (avec leur coût d'achat) en rendant la somme reçue **plus une pénalité qui croît avec le temps** (`cancellation.saleSteps` de `economy.json` : 5 % ≤ 5 min, 10 % ≤ 1 h, 25 % ≤ 1 jour, 50 % ≤ 3 jours, 75 % ≤ 2 semaines, 90 % au-delà). Il faut avoir les Sceaux ; une seule fois.
- **Annuler un achat** : seulement contre le clic malheureux, dans les 5 minutes et si tous ses boosters sont encore scellés, remboursé moins 5 %. Au-delà, la revente au Boosterium existe ; un remboursement au prix payé plus tardif serait une assurance gratuite contre la baisse du marché.
- Les compteurs d'achievements (ex. cartes vendues) ne sont pas décomptés par une annulation.

## 8 ter. Parties, sauvegardes et écrans

- **Accueil** au lancement (titre, accroche, menu) : Continuer (la partie ouverte, sinon la dernière jouée), Nouvelle partie, Charger une partie (renommer, supprimer), Options, À propos, Quitter (en plein écran, la fenêtre n'a pas de barre de titre pour la fermer). Pendant le jeu, « Menu » revient à l'accueil sans fermer la partie.
- **Plein écran** : par défaut, comme un jeu ; « Affichage » dans Options (Plein écran / Fenêtré, `app/src/fullscreen.ts`). La fenêtre s'ouvre **cachée** (`visible: false` de `tauri.conf.json`) et le Rust l'affiche directement dans l'affichage choisi (`display.json` du dossier de configuration de l'app, écrit par la commande `set_display_fullscreen`) : avant, elle s'ouvrait toujours en plein écran, écran de chargement compris, puis repassait en fenêtré. Le choix est aussi gardé dans le `localStorage`, et l'interface les resynchronise au démarrage. F11 bascule à tout moment et retient le choix. Permissions `core:window:allow-set-fullscreen` et `core:window:allow-close` (`capabilities/default.json`).
- **Une partie = un fichier SQLite** dans `saves/` (`app/src-tauri/src/saves.rs`), qui se décrit lui-même dans sa table `save_meta` (nom, dates). Plusieurs joueurs d'une même machine ont chacun leur partie ; pas de notion de profil pour l'instant.
- **Sauvegarde automatique** : chaque action est enregistrée aussitôt. **Sauvegarde manuelle** = « Save point » : une copie de la partie (`VACUUM INTO`), chargeable plus tard ; elle compte comme jouée juste avant l'originale, pour que « Continuer » reprenne l'originale.
- L'ancienne sauvegarde unique (`unsealed.sqlite`) est adoptée comme première partie au premier lancement, puis renommée en `.migrated`.
- **Chargement** : écran de démarrage inline dans `index.html`, avec le vrai logo (injecté au build par le plugin `splashLogo` de `vite.config.ts` depuis `logoSvg.ts`, sa police Cinzel déclarée dans le même `<style>`) et fond de fenêtre sombre (`backgroundColor`) pour éviter tout écran blanc ; composant `Loading` sur chaque écran qui attend des données.
- **À propos** : description, gratuité et absence de valeur réelle, notice de la Fan Content Policy mot pour mot (`app/src/legal.ts`), crédits Scryfall et MTGJSON, puis la section « Licence » (code sous GPL v3.0 ou ultérieure, créations sous CC BY-NC-SA 4.0, nom et logo non concédés comme marques, polices et contenus tiers sous leurs propres conditions) avec un bouton vers `LICENSE-ASSETS` sur GitHub. En haut, la communauté « The Boosterium » avec un bouton vers le Discord ; en bas de page, un bouton vers le code source sur GitHub (`MrGrabazu/unsealed`). Chacun porte le logo du service (tracés Simple Icons, CC0), ouverts dans le navigateur par `tauri-plugin-opener`.

## 8 ter bis. Identité visuelle

- **Écran du « Comptoir »** (`app/src/comptoir.css`, chargé après `theme.css` ; maquettes validées dans `.cache/da/v3.html`, non commitées) : le jeu est un **écran fixe**, comme un jeu vidéo et non une page web (`.game`, rien ne défile hormis l'intérieur des panneaux) :

## 8 quater. Langues

- **Interface** en anglais, français, allemand, espagnol et italien. Module maison sans dépendance : `app/src/i18n/` (`en.ts` = référence ; `fr.ts`, `de.ts`, `es.ts`, `it.ts` typés `Messages`, donc **TypeScript refuse une langue incomplète**). `t(clé, { variables })`, `plural(base, n)` (clés `_one` / `_other` via `Intl.PluralRules`), dates et nombres au format de la langue.
- **Choix** dans Options, mémorisé dans le `localStorage` ; par défaut la langue du système si elle est proposée, sinon l'anglais.
- **Achievements** : l'anglais vit dans `config/achievements.json`, les traductions dans `config/achievements.<langue>.json` (id → nom et description), surchargeables depuis le dossier de données. Un test vérifie que chaque fichier couvre exactement les achievements définis : **ajouter un achievement oblige à le traduire**. Les récompenses sont renvoyées en données et formulées par l'interface.
- **Langue des cartes et des sets** : réglage séparé (Options), « comme l'interface » par défaut, en anglais, français, allemand, espagnol, italien ou japonais (`FOREIGN_LANGUAGES` du core). Au build, chaque carte garde ses impressions traduites (`foreign` : nom et `scryfallId` de l'impression, depuis le `foreignData` de MTGJSON) et chaque set ses noms traduits (`names`, depuis `translations`, rempli pour ~146 sets seulement). Beaucoup d'impressions traduites n'ont chez Scryfall qu'un petit scan (`image_status: lowres`, agrandi donc flou) ou aucune image (`missing`) : l'image traduite n'est montrée que si elle est connue comme un bon scan (`highres_scan`), sinon c'est l'image anglaise, avec le nom traduit (`localized`). La qualité est demandée à Scryfall par set (`check_set_images`, `/cards/collection` par lots de 75, à l'affichage de la collection d'un set, d'un booster scellé, avant une ouverture rapide) et retenue dans `image-quality.json` du dossier de données ; le texte de la fiche vient toujours de l'impression traduite. Le jeu affiche nom et image traduits quand ils existent, sinon l'anglais, carte par carte (les vieux sets n'ont été imprimés qu'en anglais). Les prix restent ceux de l'impression anglaise. Le réglage vit dans la session Rust (`set_card_language`), envoyé par l'interface au démarrage et à chaque changement.
- **Format des données** : `DATA_FORMAT_VERSION` (core) est écrit dans le manifest ; s'il change, l'app reconstruit ses données au lancement suivant.
- **Restent en anglais** : les noms « Unsealed », « Crack & Collect » et « Boosterium », la notice de la Fan Content Policy (texte officiel, affiché tel quel, suivi de sa traduction : `FanNotice` de `Footer.tsx`, clé `legal.noticeTranslated`, vide en anglais ; dans À propos, d'une explication traduite) et les messages d'erreur venant du Rust (le système). Les étapes du téléchargement des données sont envoyées en anglais par le Rust et traduites par l'interface (`stepText` de `DataStatus.tsx`, liste fermée `STEPS` + « Preparing X (i/n) » : un nouveau message de progression doit y être ajouté) ; une erreur du build est préfixée de son étape (`build` du builder), traduite elle aussi.
- **Téléchargements** (`download` du builder) : une connexion coupée en route (Wi-Fi, veille, antivirus, « Descripteur non valide (os error 6) » de la pile réseau de Windows) est reprise jusqu'à 5 fois, là où elle s'était arrêtée si le serveur accepte une requête `Range`, sinon depuis le début.
- **Ajouter une langue** : un fichier `app/src/i18n/<code>.ts`, une entrée dans `LANGUAGES` et `MESSAGES` (`i18n/index.tsx`), un `config/achievements.<code>.json`, et une ligne dans `ACHIEVEMENT_TRANSLATIONS` (`lib.rs`) et dans le test des traductions.

## 8 quinquies. Fiche détaillée d'une carte

- **Mise en page** : la fiche ne dépasse jamais de la fenêtre (`.modal.details` de `comptoir.css`) : l'image à gauche, sa largeur bornée pour tenir en hauteur ; à droite le texte (jusqu'à 55 % de la hauteur, il défile au-delà) puis les impressions, qui défilent seules (`.printing-list`, avec son retour en haut) : un terrain de base en a des centaines. Les fenêtres (fiche, vente conclue, vente en lot) sont rendues à la racine de la page (`Backdrop.tsx`, portail) : dans la scène, elles restaient sous la sangle du haut.
- **Ouverture** : clic sur une carte de la Collection. La fiche montre la grande image, le texte de chaque face (coût en symboles de mana, type, texte, texte d'ambiance, force/endurance ou loyauté), l'artiste, les prix du marché normal et foil, ce que le Boosterium en donne, les exemplaires possédés, et **toutes les impressions** de la carte (set, numéro, année, prix du jour, « dans le jeu », exemplaires possédés).
- **Source** : la partie locale vient des données du jeu ; le texte et les impressions viennent de l'**API Scryfall à la demande** (`core/src/scryfall.rs`), avec cache mémoire pour la session et au moins 100 ms entre deux requêtes (conditions de Scryfall). La commande Tauri est asynchrone et n'appelle le réseau ni sur le fil principal ni en tenant la session. Hors ligne, seule la partie locale s'affiche.
- **Langue** : le texte vient de l'impression dans la langue des cartes quand elle existe (`printed_*`), sinon du texte Oracle anglais.
- **Cartes double face** (transform, modal double face, réversible, bataille…) : bouton « Retourner » sur la fiche, dans la Collection et à l'ouverture (une fois la carte révélée). L'image du dos vient du CDN Scryfall (`/back/`).
- Test réseau à la demande : `cargo test -p unsealed-core --test scryfall_live -- --ignored`.

## 9. Fonctionnalités de collection

- Vue par set avec **pourcentage de complétion** et cartes manquantes affichées en grisé.
- **Tous les sets** (première entrée de la liste des sets) : toutes les cartes possédées en une grille, chacune avec son set, triable (prix de la finition possédée croissant ou décroissant, rareté, nom, set, nombre d'exemplaires) pour repérer vite quoi vendre. Côté jeu `owned_everywhere` : chaque carte est cherchée dans le fichier du set du booster qui l'a donnée (`owned_card_sources`, d'après les ouvertures enregistrées), sinon de son propre set, sinon de son set parent (« TLTR » → « LTR »).
- **Vente en lot** (« Vendre… », à côté des doublons, sur un set) : fenêtre `SellPicker.tsx`, une ligne par choix (toutes les cartes, communes, peu communes, rares, mythiques, autres raretés, jetons, cartes d'art) avec le nombre d'exemplaires et le montant, « Garder un exemplaire de chaque carte » coché par défaut (comme pour les doublons : le foil est gardé s'il y en a un), second clic pour confirmer, puis la fenêtre « Vente conclue ». Côté jeu, un simple `sell_cards` (atomique).
- **Un set** (vue « Par set ») : écran partagé, le classeur ou la grille à gauche (cadre au nom du set), à droite le panneau « Complétion » : symbole, nom, année, **anneau doré** de la complétion (celle de la section ouverte du classeur, nommée sous l'anneau), le détail par rareté, valeur et rachat, puis « Revendre les doublons · montant » (doré), « Vendre… » et « Acheter des boosters de ce set ». **Toute la page défile** (pas seulement le classeur ou la grille : `.split.flow`, la scène elle-même défile) et le panneau « Complétion » reste collé en haut (`position: sticky`, `top: 0` : il compte depuis le padding de la scène, aligné ainsi sur le cadre de gauche), à la hauteur visible de la scène (son contenu défile à l'intérieur). La bibliothèque et « Tous les sets » sont dans un seul grand cadre.
- **Acheter des boosters de ce set** (panneau « Complétion ») : ouvre le Boosterium sur ce set, choisi et en vue, filtres remis à zéro (`focus` de `Boosterium.tsx`).
- **Barre de la Collection** (une seule ligne compacte, `.collection-bar.compact`) : « Bibliothèque | Par set | Par artiste » à gauche, puis les filtres de la vue affichée (set, artiste et recherche, tri, filtre de la grille), qui rétrécissent au besoin, et « Classeur | Grille » à droite quand ils s'appliquent (les ventes d'un set sont dans son panneau « Complétion »).
- **Bibliothèque** (premier choix de la Collection, avant « Par set » et « Par artiste », affichée par défaut) : une étagère en bois où chaque set dont on possède au moins une carte (jetons et cartes d'art compris) a son classeur debout, du plus ancien au plus récent (`Library.tsx`). La tranche reprend la couverture du classeur (`coverOf` de `Binder.tsx` : même teinte, même matière, les règles CSS `[data-cover]` servent aux deux), avec le symbole du set en haut, son nom sur une étiquette de papier (taille adaptée à la longueur, jusqu'à 3 lignes) et son code en bas ; l'épaisseur suit le nombre de pages du classeur (9 cartes par page : de 34 px pour un petit set à 110 px), la hauteur varie un peu selon son code, un set complet a un filet doré. Les classeurs sont serrés (2 px d'écart, 6 px des montants) et chaque étagère en reçoit autant que sa largeur le permet, la rangée étant centrée ; au moins deux étagères. Au survol, une fiche suit la souris : complétion, rares et mythiques, extras collector, jetons et cartes d'art, exemplaires (dont foil), boosters ouverts, valeur marché, rachat au Boosterium et meilleure carte. Un clic ouvre le classeur du set (vue Classeur). Côté jeu : `Game::library` (`game/library.rs`, commande `get_library`), calculé à la demande depuis `collection()` de chaque set possédé.
- **Collections par artiste** (« Par set / Par artiste » en haut de la Collection), avec le même panneau « Complétion » collant qu'un set (initiales en médaillon, années de la première à la dernière carte, anneau, détail par rareté jetons et cartes d'art compris, valeur et rachat, revente des doublons par `sell_cards` et « Vendre… ») : toutes les cartes qu'un artiste a illustrées dans les sets proposés (jetons et cartes d'art compris), de la plus ancienne à la plus récente, en classeur ou en grille, avec leur complétion. Index construit au build (`artists.json`, `artist_index` : une carte par uuid, rangée sous chacun de ses artistes, « A & B » comptant pour les deux, avec le set qui la contient) ; côté jeu `game/artists.rs` (`artists`, `artist_collection`). Liste des artistes triée par nombre de cartes, avec recherche insensible aux accents.
- **Revente des doublons** : une fenêtre « Vente conclue » (`SaleModal.tsx`) montre le total en grand, le nombre de cartes et le détail (vignette, nom, foil, quantité, prix unitaire, montant), du plus rentable au moins rentable. Le détail est calculé côté interface depuis la collection affichée juste avant (`duplicatesOf`, même règle que `Game::sell_duplicates` : un seul exemplaire gardé par carte, toutes finitions confondues, le foil s'il y en a un ; tout le reste part s'il est rachetable). La vente d'une seule carte garde une simple ligne de notification.
- **Deux affichages** au choix (mémorisé dans le `localStorage`, `settings.ts`) : **Classeur** par défaut, ou **Grille** en second choix (filtres, vente carte par carte). Le classeur (`Binder.tsx`) a une couverture propre à chaque set, couleur et matière (cuir grainé surpiqué, toile, vinyle brillant, suédine) tirées de son code : toujours la même, rien à stocker (`coverOf`, `.binder-spread[data-cover]`). Il montre des pages de 9 pochettes (3×3), deux pages en vis-à-vis, chaque carte à sa place dans l'ordre des numéros. Une carte manquante est un bout de papier découpé à la va-vite glissé dans la pochette, avec son nom (langue des cartes) et son numéro écrits à la main (polices manuscrites du système : Ink Free, Segoe Print, Bradley Hand…), découpe, inclinaison, encre et taille tirées de l'uuid (une carte garde toujours le même papier). Hormis ces papiers, rien n'est écrit sur les pages, comme dans un vrai classeur : ni titre de section ni légende, le numéro, le nom et le prix apparaissent sur la carte au survol. Les sections (cartes, extras collector, jetons) commencent chacune sur une nouvelle page, avec un onglet au-dessus du classeur pour y sauter (celui de la section affichée est surligné) ; la barre de complétion suit la section affichée (« Jetons · 5 / 18 »), car jetons et extras se collectionnent aussi ; on tourne avec les deux grandes flèches sur les côtés du classeur ou ←/→, sans animation, le numéro des pages étant rappelé dessous (une animation de feuille a été essayée puis abandonnée). Un clic ouvre la fiche. Les colonnes sont en `minmax(0, 1fr)` : en `1fr`, une image chargée à sa taille réelle élargit sa colonne et casse la mise en page.
- **Ensembles** (« Groups » en anglais, « Sets » prêtant à confusion) : tout ce qui se collectionne à l'intérieur d'un set, de trois sortes (`GroupKind` du core, `custom` pour les nôtres) : les **cycles** du wiki, les **récits** (Story Spotlights : l'histoire du set carte après carte, dans son ordre ; 37, dont les 3 actes de War of the Spark, d'après la liste du wiki collée dans `.cache/story-spotlights.txt`, ses noms collés sans séparateur découpés par `build-cycles.js` d'après les cartes du set, le plus long d'abord, deux fautes de frappe du wiki corrigées) et **les nôtres** (sceau « U »). Badges : ◆ doré, ¶ parchemin, U de cire. La vue filtre par sorte (si le set en a plusieurs) et par état. Les succès des cycles ne comptent que les cycles : un récit complet émet `StoryCompleted` (mêmes champs), pour de futurs succès ; `CyclesProgress` ne compte que les cycles.
- **Cycles** (sous-collections d'un set : les cinq Dieux d'Amonkhet, ses Cartouches, les dragons chromatiques de Forgotten Realms…) :
  - **Référentiel du wiki** : `config/cycles.json`, **généré, jamais édité à la main**. `node .cache/wiki-crawl.js` récupère chez soi la page MTG Wiki de chaque set proposé dans `.cache/wiki/sets/<CODE>.txt` (API du wiki, 50 pages par requête, une par seconde ; le wiki refuse les requêtes venant de Claude, d'où un script à lancer soi-même ; plan B : `Special:Export` dans un navigateur puis `--import`). Ensuite `node .cache/build-cycles.js` lit la section « Cycles » de chaque page (un tableau, une ligne par cycle ; les cartes y sont écrites `{{card|…}}` ou `<c>…</c>` selon les pages, Ikoria par exemple), retrouve chaque carte par son nom parmi les cartes du set lui-même (ni jetons, ni cartes d'art, ni invitées ; apostrophes, Æ, cartes scindées et faces arrière normalisées) et liste les noms introuvables, surtout des cycles de bloc qui citent les sets voisins. On ne garde que des faits (nom, cartes) : les textes du wiki y restent. Environ 1 540 cycles dans 162 sets.
  - **Emplacements par numéro** : un cycle est une liste d'emplacements (une carte), chacun donnant les **numéros de collection** de ses impressions dans le set, de la moins à la plus premium (normale < cadre spécial (showcase, sans bordure, étendu) < full art < numérotée, avec un cran de plus pour une impression foil seulement). En jeu, l'emplacement montre le plus bel exemplaire possédé : rang = place de l'impression × 2 + foil. Il est « de prestige » quand c'est la dernière impression, en foil si elle existe.
  - **Nos cycles** : `config/cycles.custom.json`, jamais écrasé. On y ajoute des sous-collections (les **Neuf** de LTR, 9 emplacements « illustration normale → sa version sans bordure », appariés par artiste), on remplace un cycle du wiki (même `id`) ou on le masque (`hidden`, « SET/id »). Noms par langue.
  - **Noms traduits** : `config/cycles.<lang>.json`, nom anglais → traduction, pour les ~1 200 noms distincts. Liste à traduire : `node .cache/cycle-names.js` (et les seuls noms nouveaux : `node .cache/cycles-stats.js`) ; contrôle : `node .cache/check-cycle-translations.js fr`. Un test exige que chaque nom soit traduit dans les 4 langues.
  - **Code** : core `core/src/cycles.rs` (fusion, validation, nom par langue ; tests `core/tests/cycles.rs`) ; jeu `game/cycles.rs` (commande `get_cycles`, partagé par les parties d'une session). Un fichier du même nom dans le dossier de données remplace celui livré. Les jetons du set portent parfois son code et les mêmes numéros que ses cartes (FRA, LTR) : ils sont écartés de la table des numéros.
  - **Écran** : un 3ᵉ affichage de la Collection d'un set, « Classeur | Grille | **Ensembles** » (seulement si le set en a ; maquette `.cache/da/v8.html`). Une plaque par cycle (pastille dorée ◆ : cycle du wiki ; sceau rouge « U » : le nôtre), sa jauge, ses cartes côte à côte (le papier manuscrit du classeur pour une manquante, le reflet foil, une étoile pour la version la plus premium), filtres Tous / En cours / Complets / À commencer ; à droite, l'anneau des cycles complets, les cartes des cycles, les cycles de prestige et les presque complets.
  - **Succès** : événements `CycleCompleted` (`cycle` = « SET/id », `custom`, `slots`, `prestige`, `releasedYear`, `allMythic`, `allLands`) et `CyclesProgress` (`completed`, `total`, `allComplete`), émis avec `SetProgress` à chaque booster ; métriques `cycles_completed`, `prestige_cycles`, `cycle_sets_completed`. 16 succès : paliers de 1 à 500 cycles, tous les cycles d'1 puis de 5 sets, prestige (1 et 10), d'avant 2000, double cycle, mythique, de terrains, et deux secrets pour les Neuf. D'autres succès du même genre pourront suivre pour nos cycles.
- **Collector Boosters** : `data.json` liste les types de booster proposés (`play`, `collector`) ; chaque set garde ceux qu'il possède (le build n'échoue que si un set n'en a aucun). Changer cette liste déclenche un rebuild au lancement (`booster_kinds` du manifest). La complétion ne compte que les cartes des boosters principaux ; les cartes exclusives aux collectors (showcase, borderless, foils spéciaux) forment une section « Collector extras » à part.
- **Sortie** : un set n'apparaît (Boosterium, Collection, récompenses « latest ») qu'à partir de sa date de sortie (`read_sets(…, today)`) ; MTGJSON liste les sets à l'avance, avec des prix instables. Un booster scellé d'un set masqué reste ouvrable.
- **Types de booster inconnus** : en mode `"all"`, le build signale dans `skipped` un set qui n'a aucun booster d'un type gardé (avec les types que MTGJSON propose) et, sous la clé `CODE/main`, un set dont seuls les Collector sont gardés : Wizards renomme parfois son booster principal (le « Booster Pack » de 2027), qu'il faut alors ajouter à `boosters` de `data.json`.
- **Sets proposés** : `"sets": "all"` → tous les sets MTGJSON des types `core`, `expansion`, `masters`, `draft_innovation`, `funny` et `starter` (hors sets en ligne) qui ont un booster voulu (`play`, `draft`, `set`, `default` = booster unique des sets d'avant 1996, `collector`). Environ 178 sets, d'Alpha (1993) à aujourd'hui. Un type de booster qui échoue à la simulation est retiré seul (le set reste proposé) ; la raison est listée dans `skipped` du manifest.
- **Taux attendus sans doublon** : sur une feuille aux poids inégaux (vieux sets imprimés sur planche, une carte pouvant occuper 1 à 5 cases ; « wildcard » des Set Boosters aux poids de 1 à 55), la probabilité qu'une carte soit tirée est calculée exactement (`sim::inclusion_probabilities`, intégrale numérique dont le pas suit le poids total de la feuille), pas en n × poids / total. Tout changement de ce calcul incrémente `VALIDATION_VERSION` (builder) pour revalider toutes les configs.
- **Tirages limités** (`config/limited.json`, surchargeable depuis le dossier de données) : certaines impressions n'existent qu'en quelques exemplaires (cartes *serialized*, numérotées). L'Anneau unique LTR #0 n'existe qu'en un seul exemplaire (~1 booster collector sur 3,3 millions). MTGJSON les décrit et les place dans les feuilles des boosters, mais ne donne pas leur tirage. Le fichier fixe donc un tirage par carte (`set` + `number`, le set étant celui de la carte : les Sol Ring des Collector LTR sont dans LTC — elfique #408z 300 ex., naine #409z 700, humaine #410z 900 en foil numéroté ; 3 000, 7 000, 9 000 en non-foil non numéroté), et `serializedPrintRun` (500) pour toute impression serialized non listée (`serialized` du `CardEntry`, tiré du `promoTypes` de MTGJSON). Dans une partie, la table `limited_pulls` (migration 9) compte les exemplaires tirés. Ce compteur ne baisse **jamais**, ni à la revente ni à l'annulation d'une vente. Une carte épuisée sort de sa feuille, et une variante de booster qui ne peut plus être remplie disparaît (`open_booster_excluding`) : une fois l'Anneau trouvé, les boosters qui l'auraient contenu n'existent plus. Ces cartes se vendent comme les autres (pas de carte trophée : c'est le choix du joueur).
- **Prix de repli** : une carte sans aucun prix, ni dans l'une ni dans l'autre finition, ni estimé d'après ses autres impressions (surtout les cartes d'art, que Scryfall ne cote presque jamais, ~2 300 ; des jetons ; quelques cartes retirées comme *Crusade*), reçoit en jeu le prix de sa rareté (`fallbackPrices` de `economy.json` : normal et foil — signée pour une carte d'art — par `common`…`mythic`, `special`, `bonus`, `token`, `art`, et `default` pour toute autre rareté), marqué « ≈ ». Toute carte est donc revendable ; l'aide quotidienne demande alors de les avoir vendues. Une carte cotée dans **une seule finition** prend ce prix pour l'autre (`Game::market_price`, et le prix à l'ouverture) : un jeton foil coté seulement en normal (Finch Formation, jeton n°6 de BLB) était sinon invendable.
- **Prix estimés** : une impression sans aucun prix Scryfall (serialized, promo rare) reçoit au build le meilleur prix de ses **autres impressions** (même `oracle_id`, hors impressions serialized), finition par finition, la finition manquante prenant l'autre (`prices_from_scryfall_jsonl`, `PriceSet::estimated`). En jeu, le prix estimé d'une carte limitée est multiplié selon son tirage (`estimateMultipliers` de `limited.json` : ×10 000 pour 1 exemplaire, ×50 jusqu'à 100, ×20 jusqu'à 500). L'interface marque ces prix « ≈ » (infobulle, et une explication sur la fiche). Un prix Scryfall réel l'emporte toujours. L'EV des boosters compte les estimations, sans le multiplicateur.
- **Tokens** : MTGJSON liste les tokens de chaque set à part (`tokens`, set « T » + code : TLTR pour LTR) et aucune feuille de booster n'en contient. La liste du set parent est parfois vide ou partielle : le build y ajoute tout le contenu du sous-set de tokens (`tokenSetCode`, sinon « T » + code ; `add_tokens_from`), sans doublon. Au build, `add_token_slots` ajoute à **chaque booster** un emplacement de token (feuilles `unsealedToken` / `unsealedTokenFoil`, tokens équiprobables) : toujours foil en Collector, sinon foil une fois sur `tokenFoilOneIn` (`data.json`, 15). Chaque variante est dédoublée (token normal / foil), donc les taux restent exacts et passent la simulation. Les tokens ont la rareté `token` (et `token: true` dans le `CardEntry`) et sont révélés en premier. Un jeton **recto verso** (le Punchcard d'Amonkhet, « Punchcard // Punchcard ») est listé par MTGJSON une fois par face sous le même numéro : `merge_token_faces` n'en garde que la face a (on la retourne dans le jeu) et donne la face b en alias (`foil_aliases`, qui sert aussi aux foils ★), pour que les parties qui l'avaient tirée la retrouvent ; sans cela le classeur gardait une pochette à jamais vide. Leur code de set est tantôt celui d'un sous-set (« TLTR »), tantôt **celui du set lui-même** (FRA, LTR dans les données actuelles) : seul le drapeau `token` les distingue, et tout ce qui compte les cartes d'un set doit les exclure explicitement (`obtainable_cards`, carte phare `featured_card`). La Collection les retrouve sous l'un ou l'autre code (`owned_with_tokens`) et en fait une section « Jetons » hors complétion. Les cartes de pub et d'art des vrais boosters ne sont pas reproduites.
- **Cartes d'art** : MTGJSON les range dans la série d'art du set (« A » + code : ALTR), parmi ses tokens, chaque carte en deux faces (a et b) ; leur version à signature dorée est la finition `signed`. Au build (`add_art_cards_from`), une entrée par carte (face a, nom simple), rareté `art`, `art: true`, la finition signée enregistrée comme « foil ». Un emplacement d'art est ajouté (`add_art_slots`, taux dans `artCards` de `data.json`, d'après le wiki) : **Set** : une carte d'art dans chaque booster, signée 1 fois sur 20 ; **Play** des sets sortis avant Aetherdrift (2025-02-14) : 30 % + 5 % signées ; **Collector** depuis Aetherdrift : 45 % + 5 % signées (non documenté, estimé). Dans un vrai Play ou Collector, la carte d'art prend la place du token ; ici elle s'y ajoute. Révélée en premier dans un Set Booster, juste avant le token ailleurs. Section « Cartes d'art » (grille et classeur) hors complétion ; la version signée a un reflet et un halo dorés (`sheenClass`) et un badge « Signée ».
- **Cartes invitées et séries invitées** : les cartes d'un **autre set** que donnent les feuilles des boosters d'un set (`SetFile::guest_cards` : code de set différent, ni jeton ni carte d'art, présente dans une feuille ; 59 sets concernés) : Special Guests « SPG », The List « PLST », séries bonus (Masterpieces « MPS »/« MP2 », Expeditions « EXP », Mystical Archive « STA », Retro Artifacts « BRR », Multiverse Legends « MUL »…), cartes du set Commander associé dans les Collector (LTC dans LTR). Chaque **série** a son propre classeur, rangé par le code de set de ses cartes et fait de ses cartes de **tous** les sets proposés : la complétion de Special Guests porte sur toute la série. Index construit au build (`guests.json`, `guest_index` : par série, nom, noms traduits, date et symbole tirés de MTGJSON et Scryfall, et chaque carte avec les sets dont les boosters la donnent, le premier détenant la carte dans son fichier) ; côté jeu `game/guests.rs` (`is_guest_series` : dans l'index, pas un set proposé, donnée par un booster d'un set proposé ; `series_collection` ; commande `list_guest_series`). Dans un classeur de série, chaque carte dit dans quels boosters on la trouve (`boosters` du `CollectionCard`), et le panneau « Complétion » liste ces sets (vers le Boosterium) au lieu d'« Acheter des boosters ». Le panneau d'un set liste ses séries invitées avec le compte possédé (`guestLinks`), qui ouvrent leur classeur. « Tous les sets » range une invitée sous le nom de sa série. Deux cas à part : (1) un set qui **garde ses invitées** (`keeps_its_guests` : au moins 3 fois plus d'invitées que de cartes à lui, soit les seuls Mystery Boosters MB1, MB2, MBC ; DMU ou MOM, riches en The List, restent sous 2) les montre dans sa section « Cartes invitées », et l'index ne les compte pas ; (2) une série qui est elle-même un **set proposé** (Theros dans Born of the Gods, Zendikar dans Worldwake…) n'a pas de classeur à part : ses cartes absentes de son fichier vont dans une section « Dans d'autres boosters » de son classeur (`cards_elsewhere`). La revente des doublons d'un classeur (`sell_duplicates`) part de sa vue : exactement les cartes qu'il montre. Avant, ces cartes n'étaient dans aucun classeur (une Eye of Ugin SPG tirée d'un booster FRA n'apparaissait que dans « Tous les sets »).
- **Versions foil « ★ »** : MTGJSON liste comme des impressions à part (numéro suivi de « ★ ») les foils de 7ED à 10E, d'Unhinged et de quelques autres sets. Au build, `merge_foil_printings` (import) fusionne chacune dans sa carte : une ★ imprimée seulement en foil, de même nom, artiste, face et set que la carte au numéro sans ★, qui elle n'a pas de foil (les ★ de WAR, planeswalkers japonais à autre illustration, restent des cartes à part). La ★ disparaît, la carte gagne la finition foil, ses feuilles (foil) tirent la carte, son prix foil vient de la ★ (`foil_scryfall_id`). Les parties sauvegardées avant gardent leurs exemplaires ★ : `foil_aliases` du fichier de set les verse dans la carte au chargement du set (`Store::merge_card`, ouvertures comprises).
- **Masterpieces** (Invocations d'AKH/HOU, Inventions de KLD/AER, Expeditions de BFZ/OGW) et foils premium des années 2000 : déjà décrits par MTGJSON (feuille `foilOrMasterpiece1In129` / `1In144`, variantes à foil), rien à ajouter.
- Historique des ouvertures et des **meilleurs tirages**.
- Statistiques personnelles (nombre de boosters ouverts, meilleure carte et sa valeur, etc.).
- *Implémenté* : onglet **Stats** (`app/src/Stats.tsx`, `Game::stats`, Comptoir) : quatre grands chiffres en médaillons (boosters ouverts avec cartes et foils, dépensé avec le rendement, valeur de la collection avec le patrimoine, meilleur booster), la **valeur moyenne par booster** en jauges dorées (les 6 meilleurs), la vitrine des 5 plus beaux tirages de tous les temps (au prix du tirage), un graphique en barres des 20 dernières ouvertures (une seule série dorée, la meilleure en surbrillance et étiquetée, la moyenne en pointillés, infobulle par barre), les comptes (valeur tirée, booster moyen, gagné en reventes, récompenses et aides, paris, cartes distinctes, pire booster) et le tableau par booster. Tout est calculé à la demande depuis `openings` / `opening_cards` (index sur les prix, migration 6).

## 10. Roadmap MVP

1. **Fondations données** : parser la clé `booster` de MTGJSON pour un set récent ; valider en Rust, par simulation, que les taux obtenus collent aux taux attendus.
2. **Import** MTGJSON + Scryfall pour 2 ou 3 sets récents en Play Booster.
3. **Ouverture animée** et ajout à la collection.
4. **Boosterium** : portefeuille, achat de boosters, revente de cartes.
5. **Achievements** : moteur événementiel et premiers paliers.
6. Ensuite : Collector Boosters, sets plus anciens, statistiques, cartes d'achievement, pipeline de distribution des données.

## 11. Règles pour l'agent

- Ne jamais introduire de mécanique liée à de l'argent réel, de la publicité conditionnant l'accès, ou un échange de valeur réelle.
- Ne jamais utiliser les logos ou marques de Wizards dans l'UI, les assets ou les noms. Seules exceptions, par décision du mainteneur (usage courant des outils de deck) : les symboles d'extension des sets et les symboles de mana, non modifiés (voir section 7). Les logos Magic: The Gathering et Wizards of the Coast restent strictement interdits.
- Garder la logique de tirage, d'économie et d'achievements en Rust, testée, avec RNG à seed.
- Tout ce qui est équilibrage (taux, prix, pourcentage de revente, récompenses) doit vivre dans des fichiers de configuration.
- Toute nouvelle config de set doit passer le test de simulation des taux avant d'être considérée comme valide.
- **Tout le code est en anglais** : commentaires, noms de fonctions/méthodes/variables/types, messages d'erreur, noms de tests. Aucun français dans le code (la documentation du projet, comme ce fichier, reste en français).
- **Commandes shell** : rester à la racine du dépôt et n'utiliser que des chemins relatifs à celle-ci (`app/src/...`, `core/src/...`, `npm --prefix app run build`). Jamais de `cd`, de `../`, de chemins `/c/...`, ni d'écriture hors du dépôt : cela déclenche des demandes de validation. Modifier les fichiers avec l'outil d'édition, jamais avec `sed`/`perl`/heredoc : le shell ne sait pas analyser ces commandes et demande une validation. Le shell sert aux commandes simples (`cargo`, `npm`, `git`). Jamais de code en ligne (`node -e "…"`, `python -c "…"`) : écrire un script dans `.cache/` puis lancer `node .cache/<script>.js`. Pas non plus de boucles, de sous-shells `$(…)`, d'aucun pipe (`| Select-String`, `| Select-Object`, `| grep`, `2>&1 |`… : lancer la commande seule et lire sa sortie entière), ni de chemin absolu même pour un simple `ls` ou pour lire un fichier hors du dépôt (journal d'une tâche de fond : attendre sa notification) (ex. vérifier qu'un programme est installé) : tout cela passe dans un script `.cache/`. Captures d'écran de l'interface : `node .cache/shot.js <page|url> <out.png>` (Edge headless).
- En cas de doute sur un schéma de données externe (MTGJSON, Scryfall), consulter leur documentation actuelle plutôt que de supposer.
